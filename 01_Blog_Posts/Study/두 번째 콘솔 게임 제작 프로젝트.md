# 두 번째 콘솔 게임 제작 프로젝트

# 📌 Console Zombie
## 1. 프로젝트 개요
- 프로젝트 한 줄 요약: 게임 엔진이나 그래픽 라이브러리 없이, Windows Terminal(윈도우 기본 터미널 프로그램)의 글자 칸만으로 1인칭 3D 화면을 그려내는 좀비 탈출 게임
- 장르 / 플랫폼: 1인칭 서바이벌 호러 / Windows Terminal
- 개발 기간: 2026-08-25 ~ 2026-09-02
- 참여 인원: 임민성
- 사용 기술 스택: C++20, Visual Studio(MSVC), Windows 기본 API(콘솔 입출력, GDI 글꼴 렌더링, XAudio2 오디오)
- 과제 조건: 쿼드트리 또는 A* 알고리즘 중 하나 이상을 게임에 실제로 사용할 것 → 이 프로젝트는 **둘 다** 사용했다
- 결과물 링크
	- GitHub: [링크](https://github.com/eruminyu/ConsoleZombie)
	- 플레이 영상: [링크](https://youtu.be/yXjKKeqMKQk?si=dSWVWn28sEbUWiIw)

## 2. 기획 목표 + 게임 플레이 흐름
### 기획 의도
- 1차 프로젝트가 "게임 하나를 시작부터 끝까지 돌아가게 만들기"였다면, 이번에는 **포트폴리오로 보여줄 수 있는 완성도**를 목표로 잡았다.
- 기능 개수를 늘리기보다, 화면을 그리는 것 · 게임의 핵심 규칙 · 적 인공지능과 환경 반응이 **서로 맞물려 돌아가는 것**을 완성도 있게 보여주는 데 집중했다.
- 전투보다 **피하고 도망치는 것**이 우선인 게임이다. 총알은 좀비 수보다 적게 주어서, "전부 쏴 죽이고 편하게 나간다"는 선택지가 아예 없게 했다.
- 이 게임의 핵심 요소는 **소리**다. 발소리, 문 여는 소리, 총소리가 좀비를 깨우고, 창문과 막힌 문에 부담을 쌓아 새로운 침입 경로를 만든다.
### 게임 플레이 흐름
- 게임 실행
	→ 실행 환경 검사 → 메인 메뉴
	→ 맵 생성 (시드라는 숫자 하나로 매번 다른 맵을 만들고, 규칙에 어긋나면 최대 100번까지 다시 만든다)
	→ 열쇠 탐색 (열쇠는 탈출구에서 "실제로 걸어가는 거리"가 가장 먼 방에 놓인다)
	→ 소음을 관리하면서 좀비를 피하고, 꼭 필요할 때만 사격
	→ 열쇠를 얻은 뒤 시작 지점 근처의 탈출구로 돌아오기
	→ 탈출 성공, 또는 좀비에게 4번 맞으면 사망
	→ 같은 맵으로 다시 하기 / 새 맵으로 다시 하기 / 메인 메뉴로 돌아가기
### 핵심 게임 규칙
- `W/S`로 앞뒤 이동, `A/D`로 시점 회전을 한다. 마우스는 시점을 돌리는 데 쓰지 않고 **화면 안에서 조준점을 움직이는 데만** 쓴다. 일반 FPS 게임과 다른 부분이다.
- 좀비는 한 발만 제대로 맞추면 죽는다. 하지만 총알은 시작할 때 4발, 맵 어딘가에 4발이 더 있어서 **합쳐서 8발**이고, 좀비는 **12마리**다.
- 총소리는 큰 소음이다. 주변 좀비를 깨우고, 창문이나 막힌 문의 침입 부담을 올린다.
- `Shift`로 달리면 스태미나가 줄어들고 발소리도 커진다. `Space`로 구르면 잠깐 동안 무적이 되어 좀비를 지나칠 수 있다.
- `E`로 닫힌 문을 열고, 깨진 창문을 넘어간다. 권총으로 문은 부술 수 없고, 멀쩡한 창문만 깰 수 있다.
- `F`를 누르고 있는 동안 뒤를 돌아본다. 이것은 **보기만 하는 것이지 겨누는 것이 아니다.** 그래서 뒤를 보는 동안에는 총을 쏠 수 없다. 뒤를 보고 → 몸을 돌리고 → 쏘는 시간이 긴장감을 만든다.
- 창문과 막힌 문은 `정상 → 경고 → 균열 → 파손`의 네 단계를 가진다. 소음이 잦아들면 경고 단계는 다시 정상으로 돌아오지만, **균열이 한 번 생기면 되돌릴 수 없다.**
- 파손된 창문이나 문 뒤에는 맵을 만들 때부터 배치된 좀비가 벽 뒤에서 기다리고 있다. 게임 도중에 아무것도 없던 곳에서 좀비가 갑자기 생기는 일은 없다.
- 시작 지점 → 열쇠 → 탈출구로 이어지는 필수 경로는 **총알을 쓰지 않아도, 창문을 깨지 않아도, 좀비를 한 마리도 죽이지 않아도** 항상 지나갈 수 있게 만들어진다.

## 3. 개발 환경 및 구조
### 프로젝트 구조
- ConsoleZombie (39개 파일, 약 12,700줄)
	- Core — 좌표, 사각형, 색상 같은 기본 자료형
	- World — 맵 타일의 규칙(`Grid`), 맵을 만드는 쿼드트리 생성기(`MapGenerator`), 만들어진 맵이 규칙에 맞는지 검사하는 검증기(`MapValidation`)
	- AI — 길 찾기와 소리 전파를 함께 담당하는 `AStar`
	- Game — 게임 상태와 화면 전환(`Game`), 플레이어 행동(`GamePlayer`), 좀비와 소음(`GameZombies`), 침입 부담(`BreachSystem`), 밸런스 수치 읽기(`Balance`), 화면 위 글자와 메뉴(`Hud`), 상태 메시지(`StatusLog`), 효과음(`AudioCues`), 자동 검사(`SelfTest`)
	- Render — 화면 픽셀 버퍼(`PixelBuffer`), 3D 화면을 그리는 레이캐스팅 렌더러(`RaycastRenderer`), 화면 결과를 숫자로 요약하는 `RenderDigest`
	- Platform — 터미널 입출력(`Terminal`), 글꼴을 픽셀로 굽는 `TextRaster`, 소리 파일 읽기(`WavFile`), 소리 출력 장치(`AudioDevice`)
- Config — `GameBalance.ini`. 좀비 수, 총알 수, 소음 크기 같은 밸런스 수치가 전부 이 파일 하나에 있다.
- docs — 작업을 시작할 때 쓰는 계획 문서 30개, 끝낸 뒤 쓰는 완료 문서 33개
### 의존 방향
- 아래층 코드가 위층 코드를 모르게 했다. 기본 자료형 → 맵 타일 규칙 → 길 찾기 → 맵 생성기와 침입 시스템 → 게임 본체 → 화면 출력 순서로, 위층은 아래층을 쓰지만 **아래층은 위층의 존재를 모른다.**
- 예를 들어 맵 타일 규칙(`Grid`)은 게임 본체(`Game`)가 무엇인지 모르고, 길 찾기(`AStar`)는 좀비라는 것이 있는지 모르며, 화면 위 글자(`Hud`)는 게임 세계가 어떻게 생겼는지 모른다.
- 1차 프로젝트에서 가장 아쉬웠던 것이 "레벨 클래스 하나에 모든 기능이 몰린 구조"였다. 이번에는 파일을 나누는 기준을 **"이 파일을 여는 사람은 무엇을 알고 싶은가"** 하나로 정했다. 플레이어가 문을 어떻게 여는지 보려는 사람이 좀비 인공지능 코드를 지나갈 필요가 없게 했다.
### 프레임마다 일어나는 일
- 키보드와 마우스 입력을 읽는다
	→ 초당 60번의 고정 주기로 게임 규칙을 처리한다 (이동, 소음, 침입 부담, 좀비 길 찾기)
	→ 별도 주기로 화면을 그린다 (초당 몇 번 그릴지는 설정 파일에서 정하고, 기본은 60)
	→ 레이캐스팅으로 화면 픽셀 버퍼를 채운다
	→ 체력이나 총알 수 같은 글자를 픽셀로 구워 그 위에 얹는다
	→ 픽셀 버퍼를 터미널 글자 칸으로 바꿔 출력한다

## 4. 주요 구현 시스템
### 터미널 글자 칸으로 픽셀 그리기
- 터미널은 원래 글자만 찍을 수 있는 프로그램이다. 하지만 글자 하나마다 글자색과 배경색을 따로 정할 수 있다.
- 그래서 모든 칸에 `▀`(위쪽 절반만 채워진 블록 문자)를 찍고, **글자색을 위쪽 픽셀, 배경색을 아래쪽 픽셀**로 썼다. 글자 칸 하나가 세로로 픽셀 두 개가 된다.
- 화면 해상도는 터미널 창의 글자 칸 수에 정확히 맞춘다. QHD 모니터에서 창을 최대화하면 약 545×139칸이 되고, 이것이 545×278 픽셀의 화면이 된다.
- 체력이나 메뉴 같은 글자도 터미널 글자를 쓰지 않는다. 터미널 글자는 크기를 게임이 정할 수 없어서 큰 모니터에서 너무 작게 보였다. 대신 **Windows에 설치된 글꼴을 GDI(윈도우의 그리기 API)로 픽셀 모양으로 구워서** 게임 화면 위에 직접 그린다.
### DDA 레이캐스팅으로 3D처럼 보이게 그리기
- 레이캐스팅은 1990년대 게임 Wolfenstein 3D가 쓴 방식이다. 진짜 3D가 아니라, 위에서 본 2D 격자 맵을 1인칭 시점처럼 보이게 그리는 기법이다.
- 원리는 이렇다. 화면의 세로 한 줄마다 플레이어 위치에서 광선을 하나 쏜다. 그 광선이 벽에 부딪힐 때까지의 거리를 재서, 가까우면 그 줄에 벽을 길게, 멀면 짧게 그린다. 이것을 화면 폭만큼 반복하면 원근감이 생긴다.
- DDA는 광선이 벽에 닿는 지점을 찾는 방법이다. 광선을 조금씩 전진시키며 검사하면 간격이 크면 벽을 뚫고 지나가고 간격이 작으면 느리다. DDA는 광선이 격자 선을 넘는 지점만 골라서 계산하기 때문에 벽을 절대 놓치지 않으면서도 빠르다.
- 광선 거리를 그대로 쓰면 화면 가장자리가 볼록하게 휘어 보이는 어안 왜곡이 생긴다. 시선 정면 기준의 수직 거리로 보정했다.
- 깊이 버퍼(화면 한 줄마다 벽까지의 거리를 기억해 두는 배열)를 두어, 좀비나 문틀이 벽보다 앞에 있으면 그리고 뒤에 있으면 가려지게 했다.
### 쿼드트리로 맵 만들기
- 쿼드트리는 공간을 네 조각으로 나누고, 필요하면 각 조각을 다시 네 조각으로 나누는 자료 구조다.
- 48×48 크기의 맵을 먼저 네 구역으로 나누고, 그중 **정확히 두 구역만** 다시 넷으로 나눈다. 그러면 최종 조각(리프)이 항상 2 + 2×4 = 10개가 된다.
- 조각 개수를 고정한 이유가 있다. 10개 조각에 "일반 방 7개, 좀비가 갇혀 있는 감염 공간 2개, 비워두는 예비 공간 1개"라는 역할을 나눠 주는데, 조각 개수가 맵마다 달라지면 그 뒤의 문 개수, 좀비 배치, 총알 배치 규칙이 전부 "경우에 따라"가 되어 버린다.
- 방은 각 조각 안에 6×6에서 10×10 크기로 놓되, 조각 가장자리에서 1칸을 띄운다. 이 여백이 없으면 이웃한 두 방이 벽을 공유해서 문이나 복도를 놓을 자리가 사라진다.
- 방들을 잇는 복도는 크루스칼 알고리즘(최소 비용으로 모든 점을 잇는 연결을 찾는 알고리즘)으로 정한다. 방 7개를 잇는 연결 6개에 우회로 2개를 더해 총 8개의 복도를 폭 2칸으로 판다.
- 맵을 만든 뒤 규칙 검사를 통과하지 못하면 시드를 바꿔 다시 만든다. 검증용 시드 64개로 재보면 평균 11번쯤 다시 만들고, 가장 운이 나쁜 시드도 38번째에는 성공했다. 제한은 100번이다.
### A* 하나가 두 가지 일을 한다
- A*는 격자 맵에서 출발점부터 목적지까지 가장 짧은 길을 찾는 알고리즘이다. 이 게임에서는 좀비가 플레이어를 쫓아올 때, 그리고 열쇠를 "탈출구에서 가장 먼 방"에 놓을 때 쓴다.
- 그런데 이 게임에서 A*는 **소리가 퍼지는 계산**에도 쓰인다. 이것이 이 프로젝트에서 기술적으로 가장 마음에 드는 부분이다.
- A*는 "목적지 쪽으로 먼저 가 보라"는 힌트(휴리스틱)를 써서 빨리 찾는다. 이 힌트를 0으로 꺼 버리면 A*는 목적지 없이 사방으로 고르게 퍼지는 다익스트라 알고리즘과 완전히 같아진다. 소리는 목적지가 없이 사방으로 퍼지니까, 힌트를 끈 A*가 곧 소리 전파다. 알고리즘을 하나 더 만들 필요가 없었다.
- 두 용도의 차이는 딱 하나다. **몸은 벽에 들어갈 수 없지만, 소리는 벽에 들어가되 비싼 값을 치른다.** 코드에서는 "이동 비용"과 "소리 비용"이라는 값 하나로 갈린다.
### 소음이 침입을 만드는 시스템
- 소리는 거리로 줄어들지 않고 **지나가는 길의 비용**으로 줄어든다. 바닥은 1, 닫힌 문은 3, 멀쩡한 창문은 4, 벽은 6이다. 총소리의 크기 30에서 지나온 비용의 1.5배를 뺀 것이 도착한 소리의 크기다.
- 예를 들어 열린 복도 10칸은 비용이 9라서 총소리가 30 − 13.5 = 16.5로 들린다. 같은 10칸이라도 사이에 벽이 세 개 있으면 비용이 24가 되어 30 − 36은 음수, 즉 들리지 않는다.
- 이 소리 계산을 **좀비, 창문·문, 플레이어의 스피커** 셋이 똑같이 쓴다. 게임 화면에 "총소리가 들린다"는 메시지가 뜨면 그것은 실제로 같은 계산에서 나온 사실이다.
- 소음이 한 번 날 때 창문마다 따로 "부담이 오를까?"를 굴리지 않는다. 먼저 "이 소음에 맵이 반응하는가"를 한 번만 판정하고, 반응한다면 소리가 크게 도착한 창문일수록 높은 확률로 하나만 고른다. 창문마다 따로 굴리면 창문이 많은 맵일수록 이유 없이 예민해지기 때문이다.
### 좀비
- 좀비의 상태는 셋이다. 벽 뒤에서 자기 창문이 깨지기를 기다리는 **대기**(완전히 멈춰 있음), 플레이어를 못 본 **미인지**, 보거나 들어서 A*로 쫓아오는 **인지**.
- 좀비가 깨어나는 계기는 넷이다. 플레이어를 보거나, 소리를 듣거나, 자기 창문이 깨지거나, 같은 감염 공간의 다른 창문이 깨지거나. 이 네 경우가 전부 `WakeZombie()`라는 함수 하나를 거치게 해서, 어느 경로로 깨어나든 울음소리와 상태 변화가 빠지지 않게 했다.
- 좀비 그림은 이미지 파일이 아니라 코드로 그린 절차 생성 스프라이트다. 걸을 때 팔다리가 움직이고, 고개를 돌리며, 죽으면 무너져서 바닥에 남는다.
- 화면에 그리는 코드와 총알이 맞았는지 판정하는 코드가 **같은 함수에서 같은 상자와 모양을 받는다.** 이 둘이 따로 계산하면 "보이는데 맞지 않는 좀비"가 생긴다. 실제로 그런 버그를 겪었고, 아래 5절에 적었다.
### 밸런스 수치는 파일 하나에서
- 좀비 수, 총알 수, 소음 크기 같은 숫자는 `Config/GameBalance.ini` 파일 하나에만 적혀 있다. 빌드할 때 이 파일 내용을 실행 파일 안에 그대로 굽고, 프로그램은 파일이 있으면 파일을, 없으면 구운 사본을 **같은 코드로** 읽는다. 코드 어디에도 손으로 적은 숫자가 없다.
- 게임 중 `F5`를 누르면 파일을 다시 읽는다. 바뀐 값은 "지금 바로 적용됨", "다음 판부터 적용됨", "다시 시작해야 적용됨" 세 종류로 나눠서 화면에 알려준다. 조용히 적용하면 "고쳤는데 왜 안 먹지"가 되기 때문이다.
- 잘못된 설정은 통째로 거부한다. 특히 총알 규칙은 "총알은 8발"이라는 고정 숫자가 아니라 **"시작 총알 + 추가 총알 < 좀비 수"라는 관계식**으로 적었다. 이렇게 하면 좀비 수만 바꿔도 "전부 죽이는 것은 불가능해야 한다"는 기획 의도가 저절로 유지된다.

## 5. 문제 해결 및 기술 도전
개발 중 작성한 완료 문서 33개에서 문제 유형별로 다섯 가지를 골랐다.

### 이슈 1 - Windows API가 "성공"이라고 답하고 실제로는 아무것도 안 하는 문제
#### 문제 상황
- 게임이 작은 창으로 뜨면 플레이어가 매번 손으로 최대화해야 했다. 코드로 창을 자동 최대화하려고 세 가지 방법을 시도했는데 전부 실패했다. 옛날 콘솔에서는 창이 오히려 작아지고 마우스까지 먹통이 됐고, Windows Terminal은 어떤 호출도 조용히 무시했다.
- 한글 글꼴이 없는 컴퓨터를 위해 글꼴 후보 목록을 만들어 뒀는데, 목록의 두 번째 후보로 넘어가는 일이 한 번도 없었다.
- 소리 출력 장치를 여는 코드가 헤드폰으로 소리를 내면서도 "출력 장치 없음"처럼 읽히는 오류를 돌려줬다.
#### 원인
- Windows Terminal은 다른 프로그램이 자기 창을 최대화하는 것을 허용하지 않는 구조였다. 애초에 밖에서 할 수 없는 일이었다.
- 글꼴을 만드는 `CreateFontW()` 함수는 **없는 글꼴 이름을 줘도 성공을 돌려준다.** 실제 글꼴 선택은 나중에 GDI가 조용히 비슷한 것으로 대체하기 때문에, 성공 여부만 보고는 원하는 글꼴이 잡혔는지 알 수 없다.
- 소리 라이브러리 XAudio2를 만드는 첫 함수는 COM(윈도우 구성 요소 체계) 초기화 없이도 성공하지만, 그다음 단계인 출력 장치 열기가 COM을 필요로 해서 거기서 실패했다.
#### 해결 과정
- 창 최대화는 포기하고 플레이어에게 맡겼다. 대신 **매 프레임 창 크기를 다시 재서 화면 해상도를 맞추게** 했다. 플레이어가 최대화하는 순간 화면이 따라간다.
- 글꼴은 만든 뒤 `GetTextFaceW()`로 **실제로 어떤 글꼴이 잡혔는지 되읽어서 요청한 이름과 비교**한다. 다르면 다음 후보로 넘어간다. 그런데 되읽은 이름이 `Malgun Gothic`이 아니라 `맑은 고딕`처럼 한국어로 돌아와서, 후보 표에 한국어 이름 칸을 따로 두었다.
- 소리는 COM을 먼저 초기화하고, 실패하면 오류 코드를 그대로 화면에 찍게 했다. "출력 장치 없음"이라는 말이 이미 한 번 틀렸기 때문이다.
- 세 번 실패한 최대화 시도는 이유와 함께 작업 지침 문서에 남겼다. 기록하지 않으면 다음 사람이 네 번째로 같은 시도를 한다.

### 이슈 2 - QHD 모니터에서 창을 최대화하면 초당 22프레임으로 떨어지는 문제
#### 문제 상황
- QHD 모니터에서 창을 최대화하면 게임이 초당 22프레임으로 느려졌다. 당연히 레이캐스팅 계산이 많아서, 또는 터미널에 보내는 글자가 많아서라고 생각했다.
#### 원인
- 둘 다 아니었다. 프레임을 터미널 출력용 문자열로 바꾸는 `ComposeFrame()` 함수가 **화면의 칸 하나마다 새 문자열 객체를 만들고** 있었다. QHD에서는 한 프레임에 7만 개다.
- 더 문제였던 것은 속도 측정기 자체가 틀려 있었다는 점이다. FPS 계산이 화면을 그린 반복에서만 시간을 재서, 노트북에서 나온 초당 434프레임은 부풀려진 숫자였다. QHD의 22프레임은 거의 모든 반복이 그리기였기 때문에 우연히 맞았을 뿐이다.
#### 해결 과정
- 문자열 객체를 만들지 않고 미리 잡아둔 버퍼에 바이트를 직접 쓰게 바꿨다. 한 프레임에 걸리는 시간이 **28.19ms에서 3.41ms**로 줄었다. 초당 60프레임의 예산이 16.6ms니까 그중 20%만 쓴다.
- FPS 측정은 그리는 반복만이 아니라 루프의 모든 반복에 대해 실제 시간을 재도록 고쳤다.
- 이어서 설정 파일의 `render_fps = 60`이 안 먹던 이유도 둘 찾았다. 하나는 시작할 때 낡은 설정 사본을 읽고 있었고, 다른 하나는 루프에서 "1밀리초만 쉬어라"고 한 것이 Windows 기본 타이머 때문에 실제로는 15.63밀리초를 쉬어서 상한이 초당 52프레임이었다. 고해상도 타이머로 바꿔 실제 대기 시간이 1.5밀리초가 됐다.
- 교훈: 느린 곳을 추측하지 말고 재라. 그리고 측정기부터 의심해라.

### 이슈 3 - 같은 사실이 여러 곳에 적혀 있어서 서로 어긋난 문제
이 프로젝트에서 **가장 많이 반복된 버그 유형**이다. 형태만 다르게 네 번 났다.
#### 문제 상황
- 밸런스 숫자를 헤더 파일에서 고쳤는데 게임이 옛날 값으로 돌았다. 그 라운드의 밸런스 작업 전체가 게임에 도달하지 못했다.
- 추가 총알을 3발에서 5발로 올렸더니 **모든 맵 생성이 실패**했다. 화면에는 "100번 시도했지만 맵을 만들지 못했다"라고만 나왔다. 원인을 찾는 데 저녁 하나를 썼다.
- 화면에 뻔히 보이는 좀비를 총으로 맞출 수 없었다. 벽 모서리 근처에서 특히 그랬다.
#### 원인
- 밸런스 숫자가 헤더 파일과 설정 파일 두 곳에 있었고, 설정 파일이 옛 값을 들고 있다가 실행할 때마다 조용히 그것을 덮어썼다.
- 총알 예산 숫자가 설정 파일, 헤더의 기본값, 맵 검증기, 자동 검사, 이렇게 다섯 곳에 흩어져 있었다. 한 곳만 올리니 맵 검증기가 "총알이 너무 많다"며 모든 맵을 거절했다. 화면에 나온 오류 메시지는 진짜 원인에서 세 단계나 떨어져 있었다.
- 좀비를 화면에 그리는 코드와 총알 명중을 판정하는 코드가 좀비의 모양만 공유하고, 좀비가 화면 어디에 얼마나 크게 있는지는 각자 따로 계산하고 있었다. 계산 방식이 미묘하게 달라서 그려진 위치와 맞는 위치가 어긋났다.
#### 해결 과정
- 밸런스 숫자는 설정 파일 하나만 원본으로 삼고, 헤더에 손으로 적혀 있던 기본값 69개를 전부 지웠다.
- 총알 예산 검사는 맵 검증기에서 빼고 설정을 읽는 곳으로 옮겼다. 역할을 잘못 나눈 것이었다. 맵 검증기는 "맵이 규칙대로 만들어졌는가"를 보는 곳이고, "이 설정이 게임으로서 말이 되는가"는 설정을 읽는 곳이 봐야 한다. 그리고 고정 숫자 대신 "총알 수 < 좀비 수"라는 관계식으로 적어서, 한쪽을 바꿔도 다른 쪽이 깨지지 않게 했다.
- 좀비의 위치와 크기를 계산하는 함수를 하나로 만들고, 그리는 코드와 명중 판정 코드가 **둘 다 그 함수에서 결과를 받게** 했다.
- 타일별 규칙(지나갈 수 있는지, 시야를 막는지, 이동 비용과 소리 비용이 얼마인지)도 코드 일곱 군데에 흩어진 `switch`문을 표 하나로 모았다. 새 타일을 추가하고 표에 빠뜨리면 컴파일 자체가 멈추게 했다.
- 교훈: **같은 사실을 두 곳에 적으면 언젠가 어긋난다.** 네 번 다 해결은 "한 곳으로 모으기"였다.

### 이슈 4 - 테스트가 통과하는데 실제로는 아무것도 검사하지 않고 있던 문제
#### 배경
- 이 프로젝트에는 `--self-test` 옵션으로 실행하는 자동 검사가 있다. 맵 생성 규칙, 소리 계산, 화면 흐름 등 19가지를 검사하고, 마지막에 "회귀를 잡는 값 셋"을 찍는다. 회귀란 코드를 고치다가 멀쩡하던 기능이 망가지는 것이다.
- 그 값 셋은 **맵 해시**(정해진 시드로 만든 맵 전체를 숫자 하나로 요약한 것), **렌더 다이제스트**(정해진 장면을 그린 화면의 모든 픽셀을 숫자 하나로 요약한 것), **HUD 다이제스트**(화면 위 글자와 메뉴 카드의 배치를 숫자 하나로 요약한 것)이다. 코드를 고친 뒤 이 세 숫자가 그대로면 맵도 화면도 글자도 바뀌지 않았다는 뜻이다.
#### 문제 상황
- 처음에는 맵 해시만 있었다. 그래서 화면을 그리는 코드를 정리할 때 화면이 그대로인지 확인할 방법이 코드 변경 내역을 눈으로 꼼꼼히 읽는 것뿐이었다.
- 렌더 다이제스트를 만든 뒤에 보니, 검사용 장면에 넣은 좀비가 **전부 살아서 깨어 있는 좀비뿐**이었다. 그러니까 잠들어 있는 좀비를 그리는 코드나 시체를 그리는 코드는 아무리 망가뜨려도 이 숫자가 움직이지 않았다.
- 좀비의 눈은 플레이어 쪽을 볼 때만 그려야 해서 "등을 보이면 눈을 그리지 않는다"는 조건문이 있었다. 이 조건문을 지워도 화면이 전혀 바뀌지 않았다. 알고 보니 그 아래 계산식이 등을 보일 때 애초에 절대 참이 될 수 없는 식이어서, **조건문이 있으나 없으나 같았다.**
- 화면 글자에 외곽선이 둘러지는지 검사하는 테스트가 글꼴을 바꾸자 실패했다. 아무것도 망가진 게 없는데도. 그 테스트는 특정 픽셀 좌표를 찔러보고 있었는데, 그 좌표에 외곽선이 있으려면 첫 글자가 왼쪽 여백 없이 딱 붙어 있어야 했다. 그건 외곽선의 성질이 아니라 **그 글꼴의 우연**이었다.
#### 원인
- 테스트가 초록불인 것과 테스트가 무언가를 실제로 보고 있는 것은 다른 일이다. 아무것도 안 보는 테스트도 초록불은 켜진다.
#### 해결 과정
- 렌더 다이제스트와 HUD 다이제스트를 만들어 "화면이 바뀌었는가"를 사람 눈이 아니라 숫자가 판정하게 했다. 이것이 성립하려면 화면을 그리는 코드에 난수나 현재 시각이 들어가면 안 된다. 그래서 좀비의 처음 방향이나 걸음 위상 같은 것도 난수 대신 좀비가 서 있는 타일 좌표에서 계산한다.
- 검사용 장면에 잠든 좀비와 시체를 섞어 넣었다.
- 눈 조건문 아래의 계산식을 고쳐서 조건문이 실제로 일하게 했고, 다시 지워 보니 이번엔 등을 보인 좀비 뒤통수에 눈이 떠서 검사가 잡았다.
- 글자 외곽선 검사는 특정 좌표 대신 "잉크 픽셀의 모든 이웃 픽셀은 잉크이거나 외곽선이어야 한다"는 규칙으로 바꿨다. 글꼴이 무엇이든 성립하는 조건이다.
- 그리고 관례 하나를 세웠다. **테스트를 쓴 다음에는 반드시 코드를 일부러 틀리게 만들어서 테스트가 빨간불을 켜는지 확인한다.** 이것을 돌연변이 테스트라고 부른다. 이 관례를 세우기 전에 발견된 눈먼 검사 넷은 전부 커밋한 뒤에 드러났고, 세운 뒤의 하나는 커밋 전에 잡았다.

### 이슈 5 - 코드는 정상인데 게임이 재미없던 문제
#### 문제 상황
- 총을 한 발 쏘면 두 방 건너에 있던 좀비까지 전부 몰려왔다.
- 기획대로 좀비 12마리 중 10마리를 감염 공간에 가두고 2마리만 밖에 두니, 맵을 돌아다녀도 아무것도 만나지 않아 조용하기만 했다.
- 스태미나가 바닥나도 계속 달릴 수 있었다.
#### 원인
- 좀비를 깨우는 함수가 거리를 전혀 보지 않았다. 총을 쏘면 맵의 모든 좀비가 깨어났다.
- 좀비 분포 숫자가 틀렸다. 코드는 기획서대로 정확히 동작했다.
- 스태미나 회복이 시작되기까지의 지연 시간을 "스태미나를 소모했을 때" 초기화했다. 스태미나가 0이면 더 소모할 수 없으니 지연이 끝나고 조금 회복되는데, 그 조금이 같은 프레임에 바로 쓰였다. 결과적으로 끊기지 않는 딸꾹질 같은 무한 질주가 됐다.
#### 해결 과정
- 좀비도 창문과 똑같은 소리 계산으로 듣게 했다. 그리고 소음 크기를 전반적으로 낮췄다(총소리 100 → 30). 소리가 닿는 거리가 66칸에서 20칸, 즉 방 하나와 옆 방까지의 복도 정도로 줄었다.
- 감염 공간에는 3마리씩 6마리만 두고 나머지 6마리를 일반 방에 흩었다. 시작 방에는 0마리, 그리고 시작 방에서 두 방 이상 떨어진 방 하나를 일부러 비워 두었다. 걸어 들어가서 스스로 찾아낸 안전한 방이 시작하자마자 주어진 방보다 값지기 때문이다.
- 스태미나 회복 지연은 **"달리려고 시도했을 때"** 초기화하게 바꿨다. 회복을 막아야 하는 것은 달리기에 성공했을 때가 아니라 달리려고 한 때다.
- 이 유형의 문제는 코드를 읽어서는 안 보이고 직접 플레이해야 드러난다. 고치는 곳은 대부분 숫자다. 그래서 게임을 끄지 않고 `F5`로 설정 파일을 다시 읽는 기능이 필요했다.

## 6. 품질을 어떻게 증명했나
### 회귀를 잡는 값 셋
자동 검사가 끝날 때마다 아래 세 숫자를 찍는다. 화면이나 맵을 일부러 바꾸는 작업이 아니라면 셋 다 이전과 같아야 한다.

| 값 | 무엇을 증명하나 | 바뀌었다면 |
|---|---|---|
| 맵 해시 | 맵 생성기가 같은 시드로 같은 맵을 만든다 | 맵 생성 규칙을 건드렸다 |
| 렌더 다이제스트 | 그 맵이 같은 방식으로 그려진다 | 화면이 바뀌었다 |
| HUD 다이제스트 | 화면 위 글자와 메뉴가 그대로다 | UI가 바뀌었다 |

- 프로젝트 후반에 코드 전체를 정리했다. 주석 2,410줄을 다시 쓰고, 흩어진 규칙을 표 셋으로 모으고, 쓰지 않는 코드를 지우고, 2,891줄이던 `Game.cpp`를 366줄로 나눴다. 그 내내 **세 숫자가 한 번도 움직이지 않았다.** 그것이 "동작을 하나도 안 바꿨다"의 증명이다.
- 세 숫자가 바뀌었을 때 설명 없이 기준값만 새 값으로 바꾸면 이 장치는 죽는다. 되돌리든가, 무엇이 어떻게 달라 보이는지 적고 바꾸든가 둘 중 하나만 허용했다.
### 자동 검사
- 검사 19개와 시드 64개에 대한 맵 생성 검사가 한 번에 돈다. 맵 생성 규칙, 타일 규칙 사이의 모순, 소리 감쇠, 창문 사격, 화면 전환, 잘못된 설정 거부, 글꼴 대체까지 검사한다.
- 맵 검증기와 자동 검사가 **같은 검사를 각자 따로 갖고 있는 곳이 하나 있다.** 중복 검출 도구가 이것을 중복으로 잡아냈지만 일부러 남겼다. 자동 검사가 맵 검증기 함수를 그대로 불러 쓰면, 검증기에 버그가 있을 때 그 버그가 자기 검사를 통과해 버리기 때문이다.
### 문서도 검사 대상이다
- 주석을 영어에서 한국어로 옮기면서 "옮겨 적기 전에 그 문장이 지금도 사실인지 코드로 확인한다"는 규칙을 세웠더니, 사실이 아닌 문장이 여섯 개 나왔다. 그중 둘은 자동 검사가 통과할 때 출력하는 문구 안에 있었다. 검사 자체는 제대로 돌고 있었고 사람이 읽는 문장만 틀려 있었기 때문에 어떤 검사도 잡지 못했다.
- 손으로 적은 숫자는 시간이 지나면 틀려진다. 맵 생성 재시도 횟수처럼 코드가 바뀌면 달라지는 수치는 문서에 적지 않고, **프로그램이 매번 직접 재서 출력하게** 하고 문서는 그 출력을 가리키기만 하게 바꿨다.

## 7. 프로젝트 결과 및 회고
### 정량적 결과
- 소스 코드 39개 파일 12,700줄, 그중 한국어 주석 2,410줄 (약 19%)
- 문서: 저장소 루트의 설명 문서 약 8,000줄 + 작업 기록 약 10,000줄 (계획 문서 30개, 완료 문서 33개)
- 화면 6종: 실행 환경 검사 · 메인 메뉴 · 맵 생성 중 · 플레이 · 일시 정지 · 사망/탈출 결과
- 맵: 48×48칸, 방 7개, 감염 공간 2개, 침입 가능한 창문과 문 3개, 넘어갈 수 있는 창문 1개
- 좀비 12마리, 총알 8발, 체력 4
- QHD 최대화 기준 한 프레임 3.41ms (디버그 빌드), 초당 60프레임 예산의 20%
- 개발자 모드: 실시간 위에서 본 지도, 맵 생성 9단계 되돌려 보기, 이동 비용과 소리 비용을 색으로 보여주는 지도, 좀비가 실제로 따라가는 경로 표시
### 정성적 결과
- 게임 엔진 없이 터미널 글자 하나를 픽셀 두 개로 써서 1인칭 3D 화면을 만들었다.
- 쿼드트리와 A*를 "과제 조건이라서 넣은" 것이 아니라, 각각 맵의 뼈대와 소리 전파·좀비 인공지능의 핵심으로 썼다.
- 타일 규칙은 표 하나에, 밸런스 숫자는 파일 하나에, 좀비의 위치 계산은 함수 하나에 있다. 같은 사실을 두 곳에 적지 않았다.
- 코드를 고친 뒤 화면이 바뀌었는지를 사람 눈이 아니라 숫자가 판정한다.

## 최종 회고
### 1차 프로젝트에서 이어진 것
1차 프로젝트 회고에 "게임의 많은 기능이 레벨 클래스 하나에 집중돼 있다"고 적었다. 이번에는 파일을 "이 파일을 여는 사람은 무엇을 알고 싶은가"를 기준으로 나눴다. 그리고 실제로 `Game.cpp`가 2,891줄까지 자랐을 때 366줄로 갈랐다. 그렇게 큰 정리를 겁내지 않고 할 수 있었던 것은, 정리하기 전에 렌더 다이제스트와 HUD 다이제스트를 먼저 만들어서 "아무것도 안 바뀌었다"를 숫자로 증명할 수단이 있었기 때문이다.

문제를 코드로 옮기기 전에 먼저 자연어로 적어 보는 습관도 이어졌다. 이번에는 그것이 작업마다 쓰는 계획 문서와 완료 문서가 됐고, 33개가 쌓였다.

### 가장 값진 교훈
총알 예산 숫자 하나를 올렸다가 저녁 하나를 날린 사건이다. 화면에 나온 오류 메시지는 진짜 원인에서 세 단계나 떨어져 있었고, 진짜 원인은 같은 숫자가 다섯 곳에 적혀 있던 것이었다. 고정 숫자로 적으면 한쪽을 바꿀 때 다른 쪽이 조용히 깨진다. **"총알은 8발"이 아니라 "총알은 좀비보다 적다"처럼 의도를 관계로 적으면 그럴 수 없다.** 이 프로젝트에서 같은 종류의 버그가 네 번 났고, 네 번 다 해결은 "한 곳으로 모으기"였다.

또 하나는 테스트가 초록불인 것과 테스트가 실제로 무언가를 검사하고 있는 것이 다르다는 사실이다. 있으나 없으나 같았던 조건문, 살아 있는 좀비만 넣어서 시체 그리기 코드를 전혀 안 보던 검사, 글꼴의 우연에 기대고 있던 검사. 전부 통과하고 있었다. 테스트를 쓴 다음 일부러 코드를 틀리게 만들어서 테스트가 실제로 잡는지 확인하는 습관은, 이 프로젝트에서 얻은 것 중 앞으로 가장 오래 쓸 것 같다.

### 아쉬웠던 점은...
좀비 그림이 코드로 그린 절차 생성이다. 픽셀 아트 파일이 준비되면 함수 하나만 바꿔 끼우면 되게 만들어 뒀지만, 결국 그림 자체는 만들지 못했다. 좀비 인공지능도 A*로 쫓아오는 것 하나뿐이라 둘러싸기나 소리로 유인하기 같은 행동은 없다.

그리고 터미널에 보내는 데이터 양이 마지막 병목이다. 창을 꽉 채우면 초당 60프레임 × 프레임당 약 295KB가 터미널이 받아들이는 속도에 아슬아슬하다. 출력 칸 수를 줄이는 설정을 마련해 뒀지만, 근본적으로는 터미널이라는 매체의 한계다.

### 그럼에도 만족스러웠던 점
처음 목표는 "기능을 늘리지 말고, 화면 그리기 · 게임 규칙 · 인공지능과 환경 반응이 맞물리는 것을 완성도 있게"였다. 소리라는 하나의 규칙이 좀비의 귀, 창문의 침입 부담, 플레이어의 스피커에 동시에 똑같이 적용되는 구조는 그 목표에 정확히 맞는다고 생각한다.

1차 프로젝트가 "게임 하나를 끝까지 돌아가게 만들기"였다면, 이번에는 "돌아가는 게임을 부수지 않고 계속 고칠 수 있는 구조 만들기"였다. 세 숫자가 그대로인 채로 12,700줄을 통째로 정리한 경험이 그 답이었다.
